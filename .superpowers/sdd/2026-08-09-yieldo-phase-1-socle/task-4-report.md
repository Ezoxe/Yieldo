## Deviation from the brief: the NOCASE collation mechanism

The brief's Step 3 instructs registering the collation via:

```python
@event.listens_for(User.__table__, "after_parent_attach")
def _use_nocase_email(table, _parent):
    table.c.email.type = String(320, collation="NOCASE")
```

**This does not work and had to be replaced.** I verified empirically (isolated
repro with a plain `sqlalchemy.Table`) that `after_parent_attach` fires once, at
the moment the `Table` is constructed and attached to its `MetaData` — which,
for a declarative model, happens as part of executing the class body itself.
By the time `User.__table__` exists as a name you can call
`event.listens_for` on, the attachment has already happened, so the listener is
registered too late and never fires. Running the brief's code verbatim leaves
`User.__table__.c.email.type` as a plain `VARCHAR(320)` with `collation is None`,
and the case-insensitive-uniqueness test failed with
`Failed: DID NOT RAISE IntegrityError`.

**Fix applied**: replaced the (non-functional) event listener with a direct,
one-time mutation at import time, right after the class body:

```python
User.__table__.c.email.type = String(320, collation="NOCASE")
```

This achieves exactly the same intent (case-insensitive email uniqueness on
SQLite databases built directly from `Base.metadata`, i.e. the test fixture,
without requiring a migration) via a mechanism that actually runs. I verified
it in isolation before touching the model file, then confirmed
`test_user_email_is_unique_case_insensitively` passes together with the rest of
the suite. The docstring/comment in `user.py` explains why the event-listener
approach doesn't work, for anyone tempted to "fix" it back.

Everything else in the brief (model field definitions, `Account`, `Category`,
`CATEGORY_TREE` contents, `seed_categories` logic, test bodies) was used
verbatim.

## Second deviation: `Account.transactions` relationship omitted

The brief's Step 4 code for `Account` includes:

```python
transactions = relationship("Transaction", back_populates="account",
                           cascade="all, delete-orphan")
```

`Transaction` is not part of Task 4's scope (no `Transaction` model exists yet;
it is presumably introduced in a later task). Declaring a relationship that
references a class name SQLAlchemy can never resolve causes a mapper
configuration error (`InvalidRequestError` / "failed to locate a name") the
first time any query touches the ORM — i.e., it would have broken every single
test in the suite, not just Account-related ones, since SQLAlchemy configures
all mappers together on first use. I omitted this relationship from
`backend/app/models/account.py`. **Whoever implements the `Transaction` model
in a later task must add this relationship back to `Account`** (and the
corresponding `account = relationship("Account", back_populates="transactions")`
on `Transaction`).

## Migration details

Command sequence (from `backend/`, using the venv's alembic):
```
.venv/Scripts/alembic.exe revision --autogenerate -m "users, accounts, categories"
```
Generated `alembic/versions/b4eec68677e6_users_accounts_categories.py`.

Because the `email` column's type was mutated to
`String(320, collation="NOCASE")` on the shared `Base.metadata` object at
import time (see deviation above), and Alembic's `env.py` does
`from app.models import *` before reading `target_metadata`, autogenerate saw
the corrected type immediately. **The generated migration already carried the
collation correctly** — no hand-editing was needed this time. I opened and
verified the file; the relevant line is:

```python
sa.Column('email', sa.String(length=320, collation='NOCASE'), nullable=False),
```

Full migration creates three tables (`users`, `accounts`, `categories`) with
their indexes (`ix_users_email` unique, `ix_accounts_user_id`,
`ix_categories_user_id`) and the `uq_category_user_slug` unique constraint, plus
the two `ondelete="CASCADE"` foreign keys on `accounts.user_id` and
`categories.user_id`/`categories.parent_id`. `downgrade()` drops them in
reverse order. Reviewed and left as generated (no manual edits required).

Applied it:
```
cd backend && .venv/Scripts/alembic.exe upgrade head
```
Output: `Running upgrade  -> b4eec68677e6, users, accounts, categories`

Verified against the actual SQLite file (`backend/data/yieldo.db`, which is
