## Deviation from the brief

**`test_builtin_rules_classify_common_french_merchants` — one amount value
changed.** The brief's literal test body calls
`classify(label, -1000, compiled)` uniformly for every case in the `cases`
dict, including `"vir salaire acme sas": "revenus-salaire"`. But
`revenus-salaire` is seeded as a `"credit"`-direction builtin rule (per
`BUILTIN_RULES`: `("revenus-salaire", "credit", ["salaire", "paie", ...])`),
and `classify` is required (careful point 3, and directly tested by
`test_income_rules_only_match_positive_amounts`) to reject a `credit`-only
rule when `amount_cents <= 0`. With every case pinned to `-1000`, the
"vir salaire acme sas" case can never match — it is mutually exclusive with
`test_income_rules_only_match_positive_amounts`, which asserts the *same*
label with a negative amount must return `None`. Both tests as literally
transcribed cannot pass under one direction-aware implementation.

I judged this an oversight in the brief's copy-pasted test body (a single
shared amount for a loop that includes both expense and income cases),
not a spec I should implement around by weakening the direction check —
weakening direction would break the more specific,
purpose-built `test_income_rules_only_match_positive_amounts`, which the
brief's careful points call out explicitly as verifying required behavior.

Fix applied — the loop now picks the amount sign based on the expected
category:
```python
for label, expected_slug in cases.items():
    # Income rules only match a credit (see test_income_rules_only_match_positive_amounts):
    # "vir salaire acme sas" needs a positive amount to hit its "credit"-direction rule.
    amount_cents = 1000 if expected_slug.startswith("revenus") else -1000
    match = classify(label, amount_cents, compiled)
    assert match is not None, f"aucune règle pour {label!r}"
    assert match.category_id == categories[expected_slug].id, label
```
Everything else in the test file (all 8 test names, all other assertions,
fixtures, imports) is verbatim from the brief. `BUILTIN_RULES`,
`CategoryRule`, `compile_rules`, `classify`, and `seed_rules` are all
reproduced verbatim with no changes.

No other deviations. `app.categorization.seed` was appended to (not
rewritten); `CATEGORY_TREE`/`seed_categories` untouched. `models/__init__.py`
export list updated per instructions. Migration required no manual
adjustment.

## Notes for later tasks

- `classify()` returns `RuleMatch(category_id, source, rule_id)` where
  `source` is the rule's `origin` verbatim (`"builtin"`, `"learned"`, or
  `"manual"`) — this is what the CSV import pipeline (a later task) should
  write directly into `Transaction.category_source`, and
  `TRANSACTION_CATEGORY_SOURCES` already accepts all three values plus
  `"rule"`, `"csv"`, `"uncategorized"`.
- `compile_rules` silently drops rules with an invalid regex, logging a
  `logger.warning` (module `app.categorization.engine`) — this is documented,
  intentional behavior, not a silent failure, and is covered by
  `test_invalid_regex_is_skipped_not_fatal`. Any later code that persists
  user-submitted regex rules should probably validate at write time too
  (not built here — out of scope for Task 9), since right now a bad regex
  is only caught at `compile_rules` time and just quietly excluded from
  matching.
- `classify` takes an already-compiled list (`compile_rules` output) and
  is meant to be called once per label using a list compiled once per
  import batch/session, not recompiled per transaction — the CSV import
  step (whichever later task wires categorisation into the parser) should
  call `compile_rules` once per user/account import and reuse it across all
  rows.
- `seed_rules` is keyed on `(pattern, category_id)` for idempotency (not
  `(pattern, category_id, direction)`), matching the DB unique constraint
  `uq_rule_user_pattern_cat` which also excludes `direction`. This means if
  a later task ever changes a builtin pattern's direction in
  `BUILTIN_RULES`, `seed_rules` will treat the existing row as already
  present and NOT update its direction — a migration/backfill would be
  needed for that scenario. Not an issue today since there is exactly one
  `BUILTIN_RULES` entry per `(slug, pattern)` pair.
- `CategoryRule.hit_count` exists in the model/migration but nothing
  increments it yet — that is presumably wired up when a later task records
  which rule matched during an actual import (not part of Task 9's scope
  per the brief).

## Fix round 1 of 5 — TotalEnergies gas bill mismatched as fuel

### Issue (from review, sourced from the corrected plan)

`backend/app/categorization/seed.py`, `logement-energie` rule group: the
pattern `"total energies gaz"` could never match. `normalize_label` strips
accents and punctuation but never inserts separators, so the brand
"TotalEnergies" always normalises to the single token `"totalenergies"`.
The `transport-carburant` entry already had this right (`"totalenergies"`,
no space). Consequence: a gas bill labelled "TOTALENERGIES GAZ PRLV"
normalises to `"totalenergies gaz prlv"`, which contains `"totalenergies"`
(fuel rule) but not `"total energies gaz"` (energy rule) — so home energy
bills were being filed as vehicle fuel.

### Fix

Changed the pattern in the `logement-energie` group from
`"total energies gaz"` to `"totalenergies gaz"` (one word, no space), with
an inline comment explaining why the space was wrong and why the longer
pattern (17 chars) still wins over plain `"totalenergies"` (13 chars) at
equal priority (100, both `origin="builtin"`). No other pattern in the file
was touched — `"casino"`, `"match"`, and `"orange"` (flagged Minor,
deferred to the final review) were left exactly as they were.
