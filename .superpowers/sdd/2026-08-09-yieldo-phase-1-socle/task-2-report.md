## Fix round 1 of 5 — CRITICAL: `db` fixture missing `poolclass=StaticPool`

### Finding

Review found that `create_engine("sqlite://", connect_args={"check_same_thread": False})` in the `db` fixture (`backend/tests/conftest.py`) had no `poolclass=StaticPool`. SQLAlchemy defaults in-memory SQLite engines to `SingletonThreadPool`, which gives each thread its own private raw connection — and for `:memory:` SQLite the connection *is* the database. FastAPI's `TestClient` dispatches sync path operations through anyio's threadpool, i.e. a different thread from pytest's. As soon as a future test exercises a DB-backed route through the `client` fixture, the route would see an empty database (`no such table`), intermittently and confusingly.

### Fix

Reproduced the bug first (see below), then applied the corrected fixture exactly as specified by the coordinator.

`backend/tests/conftest.py` — `db` fixture now imports `from sqlalchemy.pool import StaticPool` and passes `poolclass=StaticPool` to `create_engine`, with a docstring explaining why it is mandatory (not a tuning knob):

```python
engine = create_engine(
    "sqlite://",
    connect_args={"check_same_thread": False},
    poolclass=StaticPool,
)
```

### Regression test added

`backend/tests/test_db.py` — new test `test_db_fixture_is_visible_from_worker_threads(db)`:
- Creates a table and inserts a row through the `db` fixture's session (main/pytest thread).
- Reads it back from a `concurrent.futures.ThreadPoolExecutor` worker thread, using `db.get_bind()` (the fixture's engine) to open a fresh connection on that worker thread — exercising the exact cross-thread path TestClient's routes will hit, without depending on a route that doesn't exist yet (no models/routes exist before Task 4).
- Asserts the value read back on the worker thread matches what was inserted on the main thread.
